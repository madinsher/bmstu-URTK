# Семинар 1. Постановка проекта и цифровой полигон

**После лекций:** 1–2
**Продолжительность:** 2 академических часа
**Форма:** команда 3–4 человека

## Цель

Превратить расплывчатую формулировку «сделать робота, который собирает предметы» в техническое задание, из которого следуют проверяемые требования и первые проектные ограничения. Развернуть рабочую сцену в Webots.

## Что должно получиться к концу занятия

1. Техническое задание проекта (2–3 страницы).
2. Работающая сцена в Webots: робот, среда, объекты, запускается по инструкции.
3. Первая версия матрицы трассируемости — не менее семи требований.
4. Три проектных ограничения, полученных расчётом.

## Входные материалы

- Стартовый проект Webots с моделью youBot (мобильная платформа с меканум-колёсами и манипулятором 5 DOF), каталог `Содержание занятий/Занятия/Занятие 5_/youbot`.
- Шаблон технического задания и матрицы трассируемости.
- Пособие, глава 1.

## Выбор варианта проекта

Команда выбирает один из двух сквозных примеров курса.

**Вариант А — мобильный манипулятор-сборщик.** Робот обследует помещение, обнаруживает предметы двух-трёх типов, берёт целевые и раскладывает по контейнерам, возвращается на базу. Основная трудность — неопределённость.

**Вариант Б — производственная ячейка.** Два манипулятора, обрабатывающий центр, буфер, транспортный робот; общая зона перегрузки. Основная трудность — параллелизм и разделяемые ресурсы.

Вариант Б рекомендуется командам, которых интересует производственная автоматизация; вариант А — командам, которых интересует автономность и восприятие. Обе задачи проходят через все восемь семинаров.

## Задание 1. Формулировка миссии и границ (25 мин)

**1.1.** Сформулируйте миссию одной фразой, содержащей измеримый результат и срок. Плохо: «робот собирает предметы». Хорошо: «за время не более 15 минут собрать со столов все предметы типов „болт" и „гайка" и разложить в контейнеры соответствующего типа, после чего вернуться на базу».

**1.2.** Определите границы системы. Составьте таблицу:

| Внутри системы | Вне системы | Интерфейс |
|---|---|---|
| платформа, манипулятор, захват, лидар, камера, бортовой вычислитель, ПО | планировка, столы, предметы, контейнеры, оператор, питание | команда пуска, аварийный останов, отчёт |

**1.3.** Для каждого интерфейса заполните пять полей: источник, приёмник, тип данных и единицы, частота и допустимая задержка, поведение при отсутствии данных и при разрыве связи.

## Задание 2. Декомпозиция и контракты навыков (30 мин)

**2.1.** Разложите миссию на задачи, задачи — на навыки.

**2.2.** Для трёх навыков составьте полный контракт по семи полям:

```
skill <Имя>(параметры)
  params:   ...
  pre:      ...
  inv:      ...
  post:     ...
  timeout:  ...
  cancel:   ...
  recovery: ...
```

Требования к контракту:
- каждое условие в `pre` и `post` должно быть проверяемо программно — укажите, какой переменной оно соответствует;
- `inv` должен содержать хотя бы одно ограничение безопасности;
- `timeout` обоснуйте оценкой длительности, а не «на глаз»;
- `cancel` должен приводить систему в определённое состояние, а не просто останавливать;
- `recovery` должен предусматривать конечное число попыток и поведение при их исчерпании.

**Типовая ошибка:** `cancel: остановить движение`. Это не процедура: манипулятор остаётся в произвольном положении, захват в неопределённом состоянии. Правильно: `раскрыть захват, отвести манипулятор в транспортное положение, вернуть FAILED`.

## Задание 3. Требования как проверяемые свойства (25 мин)

**3.1.** Сформулируйте не менее семи требований. Каждое должно содержать пять элементов: наблюдаемую величину, условия наблюдения, процедуру измерения, критерий, последствие нарушения.

**3.2.** Классифицируйте каждое требование как свойство безопасности или живости. Обоснуйте.

**3.3.** Для требований живости укажите, как они будут проверяться (мониторингом их проверить нельзя — см. главу 1).

**3.4.** Заполните первую версию матрицы трассируемости:

| ID | Требование | Класс | Формализация | Проверка | Артефакт | Остаточный риск |
|---|---|---|---|---|---|---|

Столбцы «Формализация», «Артефакт» и «Остаточный риск» заполняются по мере прохождения курса. На этом семинаре обязательны первые пять.

## Задание 4. Расчёт проектных ограничений (25 мин)

**4.1. Бюджет задержки контура.** Выберите один критический контур (объезд препятствия либо визуальная доводка захвата). Оцените составляющие задержки:

```math
T_{\mathrm{total}} = T_{\mathrm{sens}} + T_{\mathrm{comm}} + T_{\mathrm{proc}} + T_{\mathrm{dec}} + T_{\mathrm{comm}}' + T_{\mathrm{act}}
```

Значения возьмите из документации на компоненты или из грубой оценки; на семинаре 8 они будут уточнены измерением.

**4.2.** Для контура объезда вычислите максимально допустимую скорость:

```math
T_{\max} = (d_{\mathrm{detect}} - d_{\mathrm{safe}})/v - v/(2\cdot a_{\max})
```

Найдите $v$, при которой $T_{\max} = T_{\mathrm{total}}$. Это ваше ограничение скорости.

**4.3.** Для контура захвата вычислите ошибку позиционирования, обусловленную задержкой: $\Delta = v_{\text{сближения}} \cdot T_{\mathrm{total}}$. Сравните с допуском из предусловия навыка `Grasp`. Если допуск нарушен — предложите три варианта решения и выберите один с обоснованием.

**4.4.** Оцените мощность пространства состояний вашей системы как произведение мощностей состояний компонентов. Сколько бит требуется для кодирования состояния?

## Задание 5. Развёртывание сцены (15 мин)

**5.1.** Запустите стартовый проект Webots. Убедитесь, что робот управляется, датчики публикуют данные.

**5.2.** Добавьте в сцену элементы своего варианта: столы и предметы (А) либо станок, буфер и второй манипулятор (Б).

**5.3.** Зафиксируйте конфигурацию: версия Webots, версия Python, список зависимостей, инструкция запуска в файле `README.md` репозитория проекта. Проверьте, что по инструкции сцена запускается на другом компьютере команды.

## Критерии приёмки семинара

| Критерий | Требование |
|---|---|
| Миссия | одна фраза, измеримый результат, срок |
| Границы | таблица с интерфейсами, у каждого заполнены пять полей |
| Контракты | три навыка, все семь полей, `cancel` приводит в определённое состояние |
| Требования | не менее семи, каждое с пятью элементами, классифицированы |
| Матрица | заполнены первые пять столбцов |
| Расчёты | бюджет задержки, ограничение скорости, оценка пространства состояний |
| Сцена | запускается по инструкции на другом компьютере |

## Типовые замечания

1. **Миссия без срока.** «Собрать все предметы» — не миссия, потому что не определено, когда задача считается проваленной.
2. **Требование без условий наблюдения.** «Точность 15 мм» — при каком освещении, на каком расстоянии, для какого типа предметов?
3. **Требование без последствия нарушения.** Проектировщик не знает, насколько оно критично, и не может выбрать архитектуру.
4. **Все требования отнесены к безопасности.** Обычно среди семи требований есть хотя бы одно живостное — «каждый предмет в конце концов уложен или помечен недоступным».
5. **`timeout` взят из головы.** Обоснуйте: сколько занимает операция в номинале, каков разброс, какой запас принят.
6. **Пространство состояний не посчитано.** Это пятиминутное упражнение, и его результат определяет, можно ли проверять логику вручную.
