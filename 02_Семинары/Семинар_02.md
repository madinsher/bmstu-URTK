# Семинар 2. Дискретно-событийная модель и синтез супервизора

**После лекций:** 2–3
**Продолжительность:** 2 академических часа

## Цель

Собрать модель ячейки композицией моделей компонентов, обнаружить в ней блокировку, синтезировать супервизор, гарантирующий её отсутствие, и убедиться, что синтез выводит ограничение, которое при ручном рассуждении пропускается.

## Что должно получиться

1. Модели компонентов — не менее четырёх автоматов, включая явные автоматы ресурсов.
2. Таблица классификации событий с обоснованием каждой строки.
3. Собственная реализация композиции и проверки неблокируемости на Python.
4. Найденное блокирующее состояние с восстановленным сценарием.
5. Модульные супервизоры и проверка их неконфликтности.

## Инструменты

- **Supremica** — синтез и верификация, графический редактор ([supremica.org](https://supremica.org)).
- Собственная реализация на Python — обязательна.

## Задание 1. Модели компонентов (25 мин)

**1.1.** Постройте автоматы для всех компонентов вашей системы по восьми правилам главы 2:

1. один компонент — один автомат; ресурсы тоже;
2. события — переходы, а не состояния;
3. взаимодействие только через общие события;
4. ресурс моделируется явно: Free / Busy;
5. маркированные состояния — завершение задачи;
6. отказы включены с самого начала;
7. наблюдаемость фиксируется явно;
8. неблокируемость проверяется после каждой композиции.

**1.2.** Для каждой продолжительной операции убедитесь, что ей соответствуют минимум два события — начало и завершение. Проверка: можете ли вы выразить прерывание операции посередине? Если нет — правило 2 нарушено.

**1.3.** Для каждого разделяемого ресурса постройте отдельный автомат с состояниями $\mathrm{Free} / \mathrm{Busy}_i$ и событиями захвата и освобождения.

**Минимальный состав:** вариант А — платформа, манипулятор, захват, система восприятия, зона у стола; вариант Б — $M_1, M_2$, станок, буфер, зона $Z$, конвейеры.

## Задание 2. Классификация событий (20 мин)

Заполните таблицу для **всех** событий:

| Событие | $\Sigma_c / \Sigma_{uc}$ | Механизм предотвращения | $\Sigma_o / \Sigma_{uo}$ | Источник сигнала |
|---|---|---|---|---|

Правила проверки:
- для каждого управляемого события укажите **конкретный** механизм, которым его можно предотвратить (не выдать команду приводу, не подать разрешение);
- для каждого наблюдаемого укажите датчик или программный источник;
- начала действий, как правило, управляемы; завершения, отказы и внешние воздействия — нет.

**Проверьте себя на трёх типовых ошибках:**
1. отказ объявлен управляемым;
2. завершение операции объявлено управляемым;
3. действия оператора не учтены.

Таблица проверяется построчно — большинство замечаний будет именно здесь.

## Задание 3. Реализация композиции (30 мин)

```python
def parallel(G1, G2):
    """Параллельная композиция: общие события синхронны, частные независимы."""
    ...

def nonblocking(G):
    """Возвращает (флаг, множество блокирующих состояний)."""

```

Требование: `nonblocking` возвращает **множество блокирующих состояний**, а не только флаг. Это отладочный артефакт, из которого восстанавливается сценарий.

**3.2.** Соберите модель системы композицией всех компонентов. Зафиксируйте:
- верхнюю оценку числа состояний (произведение мощностей);
- фактическое число достижимых состояний;
- отношение первого ко второму.

**3.3.** Проверьте неблокируемость. Если модель неблокирующая — усложните её так, чтобы блокировка появилась (например, добавьте второго потребителя ресурса или технологическое ограничение «станок не работает при занятой зоне»).

**3.4.** Для найденного блокирующего состояния восстановите **трассу** от начального состояния. Опишите словами сценарий, приводящий к блокировке.

## Задание 4. Синтез супервизора (35 мин)

**4.1.** Сформулируйте не менее трёх спецификаций, каждую — отдельным автоматом над минимально необходимым подалфавитом. Используйте шаблоны:

| Шаблон | Пример для вашего проекта |
|---|---|
| Взаимное исключение | зона используется одним роботом |
| Ёмкость буфера | не более $k$ деталей |
| Порядок операций | выгрузка только после обработки |
| Запрет комбинации | манипулятор не движется при движении базы |

**4.2.** Синтезируйте супервизор для каждой спецификации — в Supremica или собственной реализацией алгоритма 3.1 (итеративное удаление состояний, нарушающих управляемость, с восстановлением Trim).

**4.3.** Проверьте неконфликтность: постройте произведение супервизоров и проверьте его неблокируемость. При конфликте — объедините конфликтующие спецификации и синтезируйте монолитно.

**4.4. Обязательное упражнение.** Найдите в своей системе ограничение, которое синтез вывел, а вы при ручном рассуждении не предусмотрели. Опишите цепочку неуправляемых событий, по которой ограничение распространилось назад.

Если такого ограничения не нашлось, вероятны две причины: спецификации слишком слабые либо слишком много событий объявлено управляемыми. Проверьте таблицу классификации.

**4.5.** Оцените ограничительность: сравните $L_m(S/G)$ с $L_m(G)$. Какие полезные сценарии оказались запрещены? Обоснуйте, почему это неизбежно (или найдите ошибку в спецификации).

## Задание 5. Наблюдаемость и диагностируемость (10 мин)

**5.1.** Выберите один отказ вашей системы и объявите соответствующее событие ненаблюдаемым.

**5.2.** Постройте наблюдатель (детерминизация по ненаблюдаемым событиям). Какова оценка состояния после характерных наблюдаемых трасс?

**5.3.** Проверьте диагностируемость: существует ли неопределённый цикл? Если отказ не диагностируем, укажите минимальное изменение состава наблюдаемых событий, делающее его диагностируемым, и оцените стоимость (датчик либо таймаут с задержкой обнаружения).

## Критерии приёмки

| Критерий | Требование |
|---|---|
| Модели | $\ge 4$ автомата, ресурсы явные, отказы включены, у операций два события |
| Классификация | все события, обоснование каждой строки, механизм предотвращения указан |
| Реализация | своя композиция и проверка, возвращающая блокирующие состояния |
| Блокировка | найдена, трасса восстановлена, сценарий описан словами |
| Синтез | $\ge 3$ модульных супервизора, неконфликтность проверена |
| Обратное распространение | найдено ограничение, выведенное синтезом, цепочка описана |
| Диагностируемость | проверена для одного отказа, вывод о достаточности датчиков |

## Типовые замечания

1. **Ресурс не выделен в отдельный автомат.** Взаимное исключение «подразумевается» и потому не гарантировано.
2. **Операция моделируется одним событием.** Невозможно выразить таймаут и прерывание — контракт навыка не реализуем.
3. **Освобождение ресурса объявлено управляемым.** Супервизор «удерживает» зону занятой, что физически невозможно.
4. **Отказы отсутствуют в модели.** Все выводы относятся только к номинальному режиму, и об этом надо написать явно.
5. **Проверка возвращает только флаг.** Без множества блокирующих состояний отладка невозможна.
6. **Спецификации перекрываются по ресурсам.** Почти гарантированно дадут конфликт; объединяйте их.
