**Вариант А.** Мобильный манипулятор youBot находит предмет на столе, берёт его, отвозит в контейнер и возвращается на базу.

> **Как читать этот пример.** Основа — отчёт студентов 2024 года по той же сцене Webots (youBot, яблоко, машина состояний SMACH). Тот отчёт описывал, *что* сделано: робот ищет яблоко, объезжает препятствия, берёт его. Здесь та же задача доведена до того, что требует курс: каждое проектное решение выведено по шагам лекций 1–3, а не принято «на глаз».
>
> - Все числа в разделах 3–5 получены скриптом [`пример_отчёта/des_youbot.py`](пример_отчёта/des_youbot.py) и воспроизводятся одной командой (приложение А).
> - Значения задержек в разделе 2.6 — проектные оценки. В отчёте они помечены как оценки и уточняются измерением на этапе 8.
> - Результатов испытаний в Webots пример не содержит: в разделе 6 таблицы даны формой, которую заполняет команда. Выдумывать числа испытаний нельзя.
>
> Нумерация разделов отчёта совпадает с шагами методики. Проверяющий идёт по отчёту и по списку шагов одновременно.

## 1. Исходные данные

**Сцена.** Webots R2023b, мир `youbot.wbt`, шаг симуляции `basicTimeStep` = 16 мс. На роботе установлены:

- камера 640×480, поле зрения 1,3 рад, с узлом `Recognition` (сегментация включена);
- два датчика расстояния `ds_L`, `ds_R` на переднем бампере; таблица `lookupTable` не задана, значит действует таблица по умолчанию: дальность 0,1 м;
- манипулятор 5 степеней подвижности с датчиками положения звеньев, двухпальцевый захват.

В сцене: стол с яблоком (`Apple.proto`), контейнер, препятствия (деревянные ящики).

**Программное обеспечение.** ROS 2, пакет `webots_ros2`, исполнительная логика на SMACH. Расчёты — Python 3.7+ без внешних зависимостей.

## 2. Постановка задачи (этап 1; лекция 1, раздел 1.9 пособия)

### 2.1. Шаг 1. Миссия

> За время не более 5 минут найти яблоко на столе, взять его, положить в контейнер и вернуться на базу. Если предмет выпал и не может быть поднят, пометить его недоступным, вернуться на базу и сообщить об этом.

Измеримый результат: предмет в контейнере, робот на базе. Срок: 300 с. Исход при неудаче определён: предмет помечен недоступным. Без последнего предложения миссия не имеет завершения при отказе, и в разделе 3.8 это проявится как блокировка модели.

### 2.2. Шаг 2. Границы системы и интерфейсы

| Внутри системы | Вне системы |
|---|---|
| платформа, манипулятор, захват, камера, датчики расстояния, контроллер, супервизор | стол, яблоко, контейнер, препятствия, оператор |

| Интерфейс | Источник → приёмник | Данные и единицы | Частота, допустимая задержка | Поведение при отсутствии данных |
|---|---|---|---|---|
| команда пуска | оператор → контроллер | событие | однократно | миссия не начинается |
| аварийный останов | оператор → приводы | событие | ≤ 0,5 с до остановки | останов по таймауту сторожевого таймера 0,2 с |
| изображение | камера → распознавание | кадр 640×480, объекты с рамками | 62,5 Гц, ≤ 50 мс | через 0,5 с без кадра: `v_lost`, платформа останавливается |
| расстояние | `ds_L`, `ds_R` → контроллер | м | 62,5 Гц, ≤ 16 мс | через 0,1 с без данных: останов платформы |
| отчёт | контроллер → оператор | статус миссии, журнал событий | по завершении | — |

### 2.3. Шаг 3. Декомпозиция миссии на задачи

1. Доехать до стола.
2. Найти яблоко камерой.
3. Выдвинуть манипулятор, взять яблоко.
4. Сложить манипулятор, доехать до контейнера.
5. Выдвинуть манипулятор, положить яблоко, сложить манипулятор.
6. Вернуться на базу, сформировать отчёт.

Для отказов: при промахе захвата повторить шаг 3; при выпадении предмета пометить его недоступным и перейти к шагу 6; при препятствии перепланировать маршрут.

### 2.4. Шаг 4. Навыки и контракты

Из задач выделено пять навыков: `NavigateTo`, `Detect`, `Reach`, `Grasp`, `Place`. Ниже — контракты трёх из них, наиболее нагруженных безопасностью.

```
skill NavigateTo(target ∈ {table, box, home})
  params:   поза цели в кадре map, скорость v ≤ v_max (раздел 2.6)
  pre:      манипулятор в транспортном положении (arm_state == STOW),
            аварийный останов не активен
  inv:      min(ds_L, ds_R) > d_safe = 0,05 м,
            манипулятор не движется (arm_moving == false)
  post:     расстояние до позы цели ≤ 0,05 м, скорость платформы = 0
  timeout:  2·L/v + 10 с, где L - длина маршрута (запас на перепланирование)
  cancel:   остановить платформу с замедлением 1 м/с², вернуть FAILED
  recovery: при срабатывании датчика расстояния - перепланировать (до 3 раз),
            затем FAILED с причиной «путь заблокирован»
```

```
skill Grasp(object)
  params:   поза предмета от распознавания, подход сверху
  pre:      платформа стоит у стола (base_state == AT_TABLE),
            манипулятор выдвинут (arm_state == EXTENDED),
            предмет в поле зрения (vision == FOUND), захват открыт
  inv:      скорость сближения схвата ≤ 0,08 м/с (раздел 2.6),
            платформа неподвижна
  post:     пальцы остановлены на ширине предмета ± 5 мм (датчики finger::*),
            предмет зарегистрирован как «в захвате»
  timeout:  4 с (закрытие 1,5 с в номинале, запас ×2,5)
  cancel:   раскрыть захват, вернуть FAILED; манипулятор остаётся выдвинутым
  recovery: при промахе (пальцы сомкнулись полностью) - до 2 повторов
            с уточнением позы; затем пометить предмет недоступным
```

```
skill Place(container)
  params:   поза контейнера
  pre:      платформа у контейнера (base_state == AT_BOX),
            манипулятор выдвинут, предмет в захвате
  inv:      платформа неподвижна
  post:     захват раскрыт, предмет зарегистрирован как «в контейнере»
  timeout:  3 с
  cancel:   сложить манипулятор, не раскрывая захвата; вернуть FAILED
  recovery: нет - повтор укладки без изменения условий не имеет смысла
```

Каждое условие `pre` и `post` соответствует переменной контроллера (`base_state`, `arm_state`, `vision`), а в разделе 3 — состоянию автомата. Это не совпадение: контракт и ДЭС-модель описывают одно и то же с разных сторон.

### 2.5. Шаг 5. Требования как проверяемые свойства

Каждое требование содержит пять элементов (наблюдаемая величина, условия, процедура, критерий, последствие нарушения). В таблице они сокращены; полная форма требования R1 приведена после таблицы.

| ID | Требование | Класс | Формализация | Проверка |
|---|---|---|---|---|
| R1 | Манипулятор не движется при движении платформы | безопасность | $\mathbf{G} \neg(\text{base_moving} \wedge \text{arm_moving})$ | синтез (E1), монитор журнала |
| R2 | Предмет в захвате не теряется до укладки | безопасность | $\mathbf{G}(\text{held} \to \text{held} \mathbf{U} \text{placed})$ | см. раздел 4.6: в этой форме нереализуемо |
| R3 | Предмет либо уложен, либо помечен недоступным | живость | $\mathbf{G}(\text{detected} \to \mathbf{F}(\text{placed} \vee \text{unreachable}))$ | неблокируемость модели (3.8) |
| R4 | Миссия завершается за 300 с | безопасность с таймером | $\mathbf{G}(\text{start} \to \mathbf{F}_{\le 300} \text{done})$ | испытания, этап 8 |
| R5 | Платформа трогается только со сложенным манипулятором | безопасность | $\mathbf{G}(\text{base_start} \to \text{arm_stowed})$ | синтез (E2) |
| R6 | Захват закрывается только на видимом предмете при выдвинутом манипуляторе | безопасность | $\mathbf{G}(\text{close} \to \text{found} \wedge \text{extended})$ | синтез (E3, E5) |
| R7 | При аварийном останове движение прекращается за 0,5 с | безопасность с таймером | $\mathbf{G}(\text{estop} \to \mathbf{F}_{\le 0{,}5} \text{stopped})$ | временной автомат, этап 5 |

**Полная форма R1.** *Наблюдаемая величина:* флаги движения платформы (модуль скорости колёс > 0,01 рад/с) и манипулятора (модуль скорости любого звена > 0,01 рад/с). *Условия:* весь прогон миссии, включая отказные сценарии. *Процедура:* журнал флагов с шагом 16 мс, автоматическая проверка журнала. *Критерий:* ни одного шага, где оба флага истинны. *Последствие нарушения:* манипулятор с предметом раскачивается при разгоне платформы — возможны выпадение предмета и удар по столу.

Среди семи требований одно свойство живости (R3). Мониторингом его не проверить: по конечному журналу нельзя установить, что предмет «когда-нибудь» будет уложен. Поэтому R3 проверяется по модели — через неблокируемость.

### 2.6. Шаг 6. Бюджет задержки и проектные ограничения

**Контур объезда препятствия.** Составляющие задержки (оценки, уточняются на этапе 8):

| Составляющая | Значение | Откуда |
|---|---|---|
| $T_{\mathrm{sens}}$ — опрос датчика расстояния | 16 мс | шаг симуляции |
| $T_{\mathrm{comm}}$ — публикация через `webots_ros2` | 16 мс | шаг драйвера |
| $T_{\mathrm{proc}}$ — обработка | 2 мс | оценка |
| $T_{\mathrm{dec}}$ — решение в цикле SMACH с частотой 10 Гц | до 100 мс | период цикла |
| $T_{\mathrm{act}}$ — отработка команды приводом | 16 мс | шаг симуляции |
| **итого** $T_{\mathrm{total}}$ | **150 мс** | |

Максимальная скорость, при которой робот успевает остановиться, находится из условия $T_{\max}(v) = T_{\mathrm{total}}$:

```math
\frac{d_{\mathrm{detect}} - d_{\mathrm{safe}}}{v} - \frac{v}{2 a_{\max}} = T_{\mathrm{total}}
```

При $d_{\mathrm{safe}} = 0{,}05$ м и $a_{\max} = 1$ м/с² (оценка для youBot):

| Дальность датчика | Цикл решения | $T_{\mathrm{total}}$ | $v_{\max}$ |
|---|---|---|---|
| 0,1 м (таблица по умолчанию) | 10 Гц | 150 мс | **0,20 м/с** |
| 0,1 м | по событию | 66 мс | 0,26 м/с |
| 1,0 м (таблица задана) | 10 Гц | 150 мс | 1,24 м/с |

**Вывод.** Узкое место — не цикл SMACH, а дальность датчиков. Ускорение цикла в 6 раз даёт прирост скорости на 28 %, настройка `lookupTable` на 1 м — в 6 раз. Проектное решение: задать таблицу датчиков на 1 м, скорость платформы ограничить паспортной (0,8 м/с), цикл SMACH оставить 10 Гц.

**Контур визуальной доводки захвата.** $T_{\mathrm{total}} = 16 + 30 + 16 + 100 + 16 = 178$ мс (кадр, распознавание, передача, решение, привод). Ошибка позиционирования из-за задержки $\Delta = v_{\text{сближения}} \cdot T_{\mathrm{total}}$:

| $v_{\text{сближения}}$ | 0,05 м/с | 0,08 м/с | 0,15 м/с |
|---|---|---|---|
| $\Delta$ | 8,9 мм | 14,2 мм | 26,7 мм |

Допуск предусловия `Grasp` — 15 мм. Отсюда ограничение $v_{\text{сближения}} \le 0{,}084$ м/с, округлено до 0,08 м/с и внесено в инвариант контракта (раздел 2.4).

### 2.7. Оценка пространства состояний

Модели раздела 3 содержат 9, 4, 3, 2 и 5 состояний. Верхняя оценка — $9 \cdot 4 \cdot 3 \cdot 2 \cdot 5 = 1080$ состояний (с состоянием «недоступен»), для кодирования нужно 11 бит. Перебрать такое вручную невозможно, поэтому логика в разделе 4 вычисляется, а не пишется.

### 2.8. Итог этапа 1: проектные решения

1. `lookupTable` датчиков расстояния — на 1 м; скорость платформы — не более 0,8 м/с (раздел 2.6).
2. Скорость сближения схвата — не более 0,08 м/с (раздел 2.6).
3. Отказ «предмет выпал» получает определённый исход: пометка «недоступен» (раздел 2.1).
4. Сторожевой таймер канала датчиков расстояния — 0,1 с (раздел 2.2).

## 3. ДЭС-модель комплекса (этап 2а; лекция 2, раздел 2.9 пособия)

Разделы 3.1–3.8 соответствуют восьми правилам построения модели.

### 3.1. Правило 1. Один компонент — один автомат

**Платформа** $G_B$. Состояния: `H` — на базе (начальное, маркированное), `T` — у стола, `B` — у контейнера; `mT`, `mB`, `mH` — едет к столу, к контейнеру, на базу; `sT`, `sB`, `sH` — остановлена препятствием.

| Из | Событие | В |
|---|---|---|
| `H`, `B` | `b_go_table` | `mT` |
| `T` | `b_go_box` | `mB` |
| `T`, `B` | `b_go_home` | `mH` |
| `mT` / `mB` / `mH` | `b_arrive` | `T` / `B` / `H` |
| `mT` / `mB` / `mH` | `b_block` | `sT` / `sB` / `sH` |
| `sT` / `sB` / `sH` | `b_replan` | `mT` / `mB` / `mH` |
| `T` | `g_ok` (петля) | `T` |
| `B` | `g_put` (петля) | `B` |

Петли `g_ok` и `g_put` — физическая связь, а не требование: взять предмет можно только у стола, положить в контейнер — только у контейнера. Такие ограничения записываются в модель объекта, а не в спецификацию.

**Манипулятор** $G_A$: `S` транспортное положение (начальное, маркированное) —`a_reach`→ `R` выдвигается —`a_reached`→ `X` выдвинут —`a_stow`→ `W` складывается —`a_stowed`→ `S`. Петли `g_ok`, `g_put` в состоянии `X`: брать и класть можно только выдвинутым манипулятором.

**Захват** $G_G$: `O` открыт (начальное, маркированное) —`g_close`→ `C` закрывается; из `C` —`g_ok`→ `D` держит, либо —`g_miss`→ `O` промах; из `D` —`g_put`→ `O` положил, либо —`g_slip`→ `O` предмет выпал.

**Восприятие** $G_V$: `Sr` поиск —`v_detect`→ `F` предмет виден —`v_lost`→ `Sr`. Оба состояния маркированы: завершение миссии от восприятия не зависит.

**Предмет** $G_O$: `Tb` на столе —`g_ok`→ `Hn` в захвате; из `Hn` —`g_put`→ `Bx` в контейнере, либо —`g_slip`→ `Fl` на полу —`o_giveup`→ `Un` помечен недоступным. Маркированы `Bx` и `Un`.

**Проверка правила.** В отчёте 2024 года всё поведение было одним автоматом SMACH из пяти состояний. В таком автомате нельзя выразить, что платформа едет, пока манипулятор складывается, — поэтому такой сценарий и не проверялся.

### 3.2. Правило 2. События — переходы, а не состояния

Каждая продолжительная операция имеет событие начала (управляемое) и события завершения (неуправляемые): `b_go_*` / `b_arrive`, `a_reach` / `a_reached`, `g_close` / `g_ok`, `g_miss`. Проверка правила: можно ли выразить прерывание операции посередине? Можно — препятствие `b_block` прерывает движение платформы.

Полная классификация событий:

| Событие | $\Sigma_c$ / $\Sigma_{uc}$ | Механизм предотвращения | $\Sigma_o$ / $\Sigma_{uo}$ | Источник сигнала |
|---|---|---|---|---|
| `b_go_table`, `b_go_box`, `b_go_home` | управляемое | не выдать цель навигации | наблюдаемое | команда контроллера |
| `b_arrive` | неуправляемое | — | наблюдаемое | навигация: ошибка позы ≤ 0,05 м |
| `b_block` | неуправляемое | — | наблюдаемое | `ds_L`, `ds_R` |
| `b_replan` | управляемое | не запускать перепланирование | наблюдаемое | команда контроллера |
| `a_reach`, `a_stow` | управляемое | не выдать траекторию манипулятору | наблюдаемое | команда контроллера |
| `a_reached`, `a_stowed` | неуправляемое | — | наблюдаемое | датчики `arm1sensor`…`arm5sensor` |
| `g_close` | управляемое | не выдать команду захвату | наблюдаемое | команда контроллера |
| `g_ok`, `g_miss` | неуправляемое | — | наблюдаемое | датчики пальцев `finger::*sensor` |
| `g_put` | управляемое | не раскрывать захват | наблюдаемое | команда контроллера |
| `g_slip` | неуправляемое | — | **ненаблюдаемое** | датчика наличия предмета нет |
| `v_detect`, `v_lost` | неуправляемое | — | наблюдаемое | `Recognition` камеры |
| `o_giveup` | управляемое | не помечать предмет | наблюдаемое | решение контроллера |

**Самопроверка по трём типовым ошибкам.** Отказы (`g_miss`, `g_slip`, `b_block`) не объявлены управляемыми. Завершения операций не объявлены управляемыми. Действий оператора в этапах 1–2 нет; аварийный останов рассматривается на этапе 5 как защитный контур вне супервизора.

### 3.3. Правило 3. Взаимодействие только через общие события

| Общее событие | Автоматы | Что синхронизирует |
|---|---|---|
| `g_ok` | платформа, манипулятор, захват, предмет | взять можно только у стола выдвинутым манипулятором, и предмет переходит в захват |
| `g_put` | платформа, манипулятор, захват, предмет | положить можно только у контейнера выдвинутым манипулятором |
| `g_slip` | захват, предмет | выпадение меняет состояние обоих |

Восприятие не имеет общих событий с объектом — связь «брать только видимый предмет» не физическая, а проектная. Она появится в спецификации E3.

### 3.4. Правило 4. Ресурс моделируется явно

Разделяемый ресурс в варианте А — «право на движение»: платформа и манипулятор не должны двигаться одновременно (R1). Физически одновременное движение возможно, поэтому ресурс записан не в модель объекта, а в **спецификацию** E1 с состояниями `Free`, `Base`, `Arm` (раздел 4.3). В варианте Б роль такого ресурса играет зона перегрузки $Z$.

### 3.5. Правило 5. Маркированные состояния — завершение задачи

Маркированы: платформа `H`, манипулятор `S`, захват `O`, предмет `Bx` или `Un`, восприятие — любое. Иначе говоря, задача завершена, когда робот на базе в транспортном положении с открытым захватом, а предмет уложен или помечен недоступным. Этот выбор определяет смысл блокировки в разделе 3.8.

### 3.6. Правило 6. Отказы включены с самого начала

В модели три отказа: `g_miss` — промах захвата, `g_slip` — выпадение предмета, `b_block` — препятствие на пути. Первоначально у выпадения не было исхода: предмет на полу оставался навсегда. Раздел 3.8 показывает, что композиция это обнаруживает.

### 3.7. Правило 7. Наблюдаемость фиксируется явно

Ненаблюдаемое событие одно — `g_slip`: в сцене нет датчика наличия предмета в захвате. Датчики пальцев показывают положение, а не усилие, поэтому не отличают «держит» от «пальцы остановились в той же позе без предмета». Диагностируемость этого отказа проверена в разделе 5.

### 3.8. Правило 8. Композиция и неблокируемость

**Первая версия** — без события `o_giveup`.

| Величина | Значение |
|---|---|
| верхняя оценка $\lvert X \rvert$ (произведение мощностей) | $9 \cdot 4 \cdot 3 \cdot 2 \cdot 4 = 864$ |
| достижимых состояний | 504 |
| переходов | 2300 |
| неблокирующая | **нет**, блокирующих состояний 144 |

Кратчайшая трасса в блокировку, найденная поиском в ширину:

```
a_reach  a_reached  b_go_table  b_arrive  g_close  g_ok  g_slip
```

Конечное состояние (платформа, манипулятор, захват, восприятие, предмет) = `(T, X, O, Sr, Fl)`. Во всех 144 блокирующих состояниях предмет на полу. Сценарий словами: робот подъехал к столу, взял предмет, предмет выпал. Модели нечем завершить задачу: поднять предмет с пола нельзя, а маркированных состояний с предметом на полу нет.

Заметим, что в этой трассе манипулятор выдвинут *до* поездки к столу. Модель объекта это допускает: запрет задаётся спецификацией E2 (раздел 4.3).

**Исправление.** Добавлено событие `o_giveup: Fl → Un` — ровно тот исход, который записан в миссии (раздел 2.1) и в требовании R3.

| Величина | Значение |
|---|---|
| достижимых состояний | 648 |
| переходов | 3100 |
| неблокирующая | **да** |

Отношение верхней оценки 1080 к достижимой части 648 равно 1,7. Синхронизация по общим событиям делает недостижимой почти половину комбинаций.

## 4. Синтез супервизора (этап 2б; лекция 3, раздел 3.10 пособия)

Разделы 4.1–4.8 соответствуют восьми шагам практической методики синтеза.

### 4.1. Шаг 1. Модели компонентов

Раздел 3, версия с `o_giveup`: 648 достижимых состояний, модель неблокирующая.

### 4.2. Шаг 2. Классификация событий

Раздел 3.2. Неуправляемых событий девять: `b_arrive`, `b_block`, `a_reached`, `a_stowed`, `g_ok`, `g_miss`, `g_slip`, `v_detect`, `v_lost`.

### 4.3. Шаг 3. Спецификации

Каждое требование — отдельный автомат над минимальным подалфавитом. События вне подалфавита спецификация не ограничивает.

| Спец. | Требование | Шаблон | Состояния и переходы |
|---|---|---|---|
| E1 | R1 | взаимное исключение | `Free` —`b_go_*`→ `Base` —`b_arrive`→ `Free`; `Free` —`a_reach`, `a_stow`→ `Arm` —`a_reached`, `a_stowed`→ `Free`; в `Base` петли `b_block`, `b_replan` |
| E2 | R5 | порядок операций | `In` —`a_reach`→ `Out` —`a_stowed`→ `In`; `b_go_*` разрешены только в `In` |
| E3 | R6 | запрет комбинации | `N` —`v_detect`→ `Y` —`v_lost`→ `N`; `g_close` разрешён только в `Y` |
| E5 | R6 | запрет комбинации | `Nx` —`a_reached`→ `Ex` —`a_stow`→ `Nx`; `g_close` разрешён только в `Ex` |

Спецификация E5 появилась не сразу. Первый синтез выполнялся по E1–E3. Проверка разрешений готового супервизора показала, что `g_close` разрешён при невыдвинутом манипуляторе в 60 состояниях. Трасса одного из них:

```
b_go_table  b_arrive  b_go_box  b_arrive  a_reach  v_detect  g_close
```

Захват закрывается в воздухе, пока манипулятор выдвигается над контейнером. Требование R6 было записано верно, но E3 покрывала только его первую половину. После добавления E5 таких разрешений 0. **Урок:** супервизор делает ровно то, что записано в спецификациях. Проверять надо разрешения синтезированного автомата, а не только его неблокируемость.

### 4.4. Шаг 4. Модульный синтез

| Супервизор | Состояний |
|---|---|
| по E1 | 432 |
| по E2 | 648 |
| по E3 | 648 |
| по E5 | 648 |
| монолитный по E1, E2, E3, E5 | 324 (1060 переходов) |

Ни в одном синтезе не удалено ни одного состояния по управляемости: все четыре требования выполнимы запретом управляемых событий в момент нарушения. Обратного распространения здесь нет — оно появится в разделе 4.6.

### 4.5. Шаг 5. Неконфликтность

Совместная работа четырёх модульных супервизоров над объектом даёт 324 достижимых состояния, блокирующих 0. Супервизоры неконфликтны, модульная реализация допустима. Поведение совпадает с монолитным: тоже 324 состояния.

### 4.6. Шаг 6. Реализуемость: требование R2 в жёсткой форме

Требование R2 «предмет не теряется до укладки» записано спецификацией E4 без перехода по `g_slip`: выпадение запрещено.

| Итерация | Удалено по управляемости | Удалено по блокировке | Что удалено |
|---|---|---|---|
| 1 | 36 | 144 | все состояния «захват держит, предмет в захвате» |
| итог | | | **супервизор пуст** |

Цепочка рассуждения алгоритма:

1. В состоянии «держит» объект может породить `g_slip`. Событие неуправляемо, а спецификация его запрещает — все 36 таких состояний плохие.
2. Без них предмет нельзя взять, а без взятия недостижимы и `Bx`, и `Un`. Ни одно состояние не коаккуратно.
3. После Trim не остаётся ничего, включая начальное состояние.

Раздел 3.10 пособия говорит, что пустой результат означает противоречивость спецификаций либо ошибку в классификации событий. Здесь классификация верна: выпадение действительно неуправляемо. Противоречие в самом требовании — логика управления не может запретить физический отказ.

**Попытка ослабить требование.** E4′: «предмет не выпадает во время движения платформы».

| Итерация | По управляемости | По блокировке |
|---|---|---|
| 1 | 6 | 94 |
| 2 | 0 | 0 |

Супервизор непуст (224 состояния), но в нём 0 маркированных состояний с доставкой: достижим только исход «недоступен». Состояний «едет с предметом в захвате» — 0. Супервизор нашёл единственный способ исключить выпадение при движении: не ездить с предметом. Миссия формально неблокирующая, но полезного поведения не осталось.

### 4.7. Шаг 7. Ограничительность и переформулировка R2

Запреты итогового супервизора (E1, E2, E3, E5) — число состояний, в которых событие физически возможно, но запрещено:

| Событие | Запрещено в состояниях | Требование |
|---|---|---|
| `g_close` | 132 | R6 |
| `a_reach` | 108 | R1: платформа едет |
| `b_go_table` | 108 | R1, R5 |
| `b_go_home` | 108 | R1, R5 |
| `b_go_box` | 54 | R1, R5 |

Полезные сценарии не потеряны. Кратчайшая успешная миссия под надзором состоит из 18 событий:

```
b_go_table b_arrive a_reach a_reached v_detect g_close g_ok a_stow a_stowed
b_go_box b_arrive a_reach a_reached g_put a_stow a_stowed b_go_home b_arrive
```

Для R2 синтез дал однозначный вывод: **требование нельзя обеспечить логикой, его обеспечивает конструкция и восприятие.** Переформулировка:

- **R2а** (безопасность, обеспечивается конструкцией): ускорение платформы с предметом в захвате не более 0,5 м/с², усилие удержания подобрано с запасом ×2 для массы яблока. Проверка — испытания, этап 8.
- **R2б** (живость, обеспечивается логикой): выпавший предмет обнаруживается не позже 1 с и помечается недоступным либо поднимается. Для этого `g_slip` должен стать наблюдаемым (раздел 5).

### 4.8. Шаг 8. Реализация

Супервизор экспортирован в таблицу [`пример_отчёта/supervisor_youbot.json`](пример_отчёта/supervisor_youbot.json): для каждого из 324 состояний — переходы по событиям и список разрешённых управляемых событий. Исполнитель [`supervisor_runtime.py`](пример_отчёта/supervisor_runtime.py) содержит две операции и не содержит никакой логики сверх таблицы:

- `allowed(e)` — можно ли сейчас выдать команду, порождающую управляемое событие `e`;
- `observe(e)` — продвинуть состояние по наблюдённому событию.

**Связь с SMACH.** Машина состояний из отчёта 2024 года сохраняется, но теперь она решает, *что делать*, а супервизор решает, *что запрещено*:

| Состояние SMACH (2024) | Навык | Команды (управляемые события) | Ожидаемые события |
|---|---|---|---|
| `START` | — | `b_go_table` | `b_arrive`, `b_block` |
| `FIND` | `Detect` | — | `v_detect`, `v_lost` |
| `TURN` | `NavigateTo` (объезд) | `b_replan` | `b_arrive`, `b_block` |
| `CATCH` | `Reach`, `Grasp` | `a_reach`, `g_close` | `a_reached`, `g_ok`, `g_miss` |
| новые: `TRANSPORT`, `PLACE`, `RETURN` | `NavigateTo`, `Place` | `a_stow`, `b_go_box`, `a_reach`, `g_put`, `b_go_home` | `a_stowed`, `b_arrive`, `a_reached` |
| `END` | — | — | — |

Перед каждой командой SMACH вызывает `sup.allowed(e)`; при отказе команда не выдаётся, и отказ записывается в журнал. Каждый сигнал датчиков превращается в событие и передаётся в `sup.observe(e)`. Если приходит событие, невозможное в текущем состоянии, исполнитель выбрасывает `SupervisorViolation`: модель разошлась с объектом, и это дефект модели, а не логики.

Проверка исполнителя на полной миссии: конечное состояние `(H, S, O, F, Bx)`, маркировано. Попытка выдать `b_go_box` с выдвинутым манипулятором отклонена.

## 5. Наблюдаемость и диагностируемость отказа

Наблюдатель построен для поведения под итоговым супервизором при $\Sigma_{uo} = \lbrace \text{g_slip} \rbrace$.

| Величина | Значение |
|---|---|
| состояний наблюдателя | 324 |
| из них с неопределённостью «предмет в захвате или на полу» | 36 |

После наблюдаемой трассы

```
v_detect b_go_table b_arrive a_reach a_reached g_close g_ok a_stow a_stowed b_go_box b_arrive
```

оценка состояния: предмет ∈ {`Hn`, `Fl`}, захват ∈ {`D`, `O`}. Робот у контейнера не знает, везёт ли он предмет. Среди возможных дальше событий есть `o_giveup`, но у объекта оно определено только при предмете на полу. Контроллер не может решить, выдавать ли эту команду.

Различить ветви могут только два события: `g_put` (возможно лишь с предметом в захвате) и `o_giveup` (лишь с предметом на полу). Оба — команды контроллера, и выбрать между ними он должен, не зная ответа. Все остальные продолжения одинаковы в обеих ветвях. В частности, супервизор разрешает поездки «база → стол → база» и с предметом в захвате, и с предметом на полу, то есть в наблюдателе есть неопределённый цикл. По теореме 2.4 отказ **не диагностируем**.

**Проектное решение.** Минимальное изменение состава наблюдаемых событий — датчик наличия предмета: `g_slip` становится наблюдаемым. В Webots это делается одним из двух способов:

- включить `enableForceFeedback` на моторах пальцев и порог усилия;
- добавить `TouchSensor` на внутреннюю поверхность пальца.

Второй способ проще и не зависит от настройки регулятора. Стоимость решения — одно событие в модели и одна строка в таблице классификации.

## 8. Остаточные риски

1. **Бесконечное перепланирование.** Цикл `b_block` → `b_replan` → `b_block` не является блокировкой в смысле языков: из него есть путь к маркированному состоянию. Модель его не запрещает, но требование R4 он нарушает. Закрывается на этапе 5 временным автоматом или счётчиком попыток в контракте `NavigateTo`.
2. **Ложное распознавание.** Модель восприятия знает только «виден / не виден». Если камера принимает за яблоко другой предмет, R6 формально выполнено, а миссия нарушена. Рассматривается на этапе 6 (POMDP, порог уверенности).
3. **Движение без команды.** Супервизор фильтрует команды и не видит, как привод исполняет траекторию. Нарушение R1 из-за ошибки регулятора обнаружит только монитор журнала, а не предотвратит.
4. **Оценки задержек.** Значения раздела 2.6 — оценки; ограничение скорости пересчитывается после измерений на этапе 8.
5. **Один предмет.** С $k$ предметами автомат предмета становится произведением $k$ автоматов, и число состояний растёт в $5^k$ раз. При $k > 3$ нужен модульный синтез по предметам.

---

## 9. Выводы

1. Постановка задачи до всякой логики дала четыре проектных решения. Главное из них — дальность датчиков расстояния ограничивает скорость в 6 раз сильнее, чем частота цикла управления.
2. Композиция пяти автоматов сразу нашла блокировку «предмет выпал — задачу не завершить». Её закрыл исход «недоступен», заложенный в миссию.
3. Синтез по четырём спецификациям дал супервизор на 324 состояния без обратного распространения. Проверка его разрешений выявила пропущенное требование: закрытие захвата в воздухе.
4. Требование «предмет не теряется» оказалось нереализуемым логикой. Супервизор пуст, а ослабленная версия запрещает перевозку. Требование разделено на конструктивное (R2а) и логическое (R2б).
5. Выпадение предмета недиагностируемо без датчика наличия. Датчик — обязательное изменение сцены перед этапом 3.

## Приложение Б. Самопроверка перед сдачей

**Этап 1**

- [ ] Миссия: одна фраза, измеримый результат, срок, исход при неудаче.
- [ ] Каждый интерфейс: пять полей, включая поведение при отсутствии данных.
- [ ] Не менее трёх контрактов по семи полям; `cancel` приводит в определённое состояние; `timeout` обоснован.
- [ ] Не менее семи требований с пятью элементами; хотя бы одно — живость.
- [ ] Бюджет задержки посчитан; из него выведено ограничение скорости.
- [ ] Пространство состояний оценено.

**Этап 2а: ДЭС-модель**

- [ ] Автомат на каждый компонент; физические связи — петлями в модели объекта.
- [ ] У каждой продолжительной операции есть событие начала и события завершения.
- [ ] Таблица классификации: все события, механизм предотвращения, источник сигнала.
- [ ] Отказы в модели; у каждого отказа есть исход.
- [ ] Композиция вычислена программой: верхняя оценка, достижимая часть, переходы.
- [ ] Неблокируемость проверена; если была блокировка — трасса, сценарий словами, исправление.

**Этап 2б: супервизор**

- [ ] Каждая спецификация — отдельный автомат над минимальным подалфавитом.
- [ ] Модульные супервизоры и проверка неконфликтности.
- [ ] Проверены разрешения итогового супервизора, а не только его неблокируемость.
- [ ] Показан случай, где синтез удалил состояния по управляемости, и описана цепочка неуправляемых событий.
- [ ] Ограничительность: какие полезные сценарии запрещены и почему это допустимо.
- [ ] Супервизор экспортирован в таблицу; контроллер вызывает `allowed` и `observe` и не содержит запретов сверх таблицы.
- [ ] Для одного ненаблюдаемого отказа построен наблюдатель и сделан вывод о датчиках.
